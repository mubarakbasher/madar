# Browser smoke test — 2026-08-14 (all findings fixed 2026-08-15)

Live walkthrough of the real stack in Chrome: `apps/api` (:4000), `apps/web` (:3000),
`apps/admin` (:3001), against a freshly seeded local database. English (LTR) and Arabic (RTL),
dark mode throughout (the machine's OS preference is dark; see B-14).

Screenshots: `test-screenshots/2026-08-14/` (findings),
`test-screenshots/2026-08-15-fixes/` (after).

This was the first browser exercise of the **single-language data entry** change (`3811809`),
which shipped on typecheck/lint/i18n alone. It found a blocker — see B-02.

## Status

All 18 findings are fixed on `fix/smoke-2026-08-14` (6 commits), plus two defects the follow-up
investigation turned up that this report had originally **mis-read as working**:

- **B-06 was two bugs, not one.** The `$` was never a formatting bug: the seed priced plans and
  subscription invoices in USD against an EGP tenant and an EGP platform bank account. The `£` was
  a separate presentation bug — a literal typed into a `symbolFor()` helper.
- **B-19 (new).** The admin MRR card, called "correct" below, summed `plan.monthly_price_cents`
  and labelled the total with the *tenant's* currency.
- **B-04 was worse than reported.** The impersonation token did not survive the handoff redirect at
  all, so the "impersonation" session was actually the target user's own session with a cosmetic
  banner — actions were not attributed to the impersonator.

Every fix was re-verified in the browser against a clean `db:reset && db:seed`. Two dev-environment
gotchas cost real time and are worth knowing: Next's Fast Refresh frequently served **stale
bundles** (a hard reload was needed before trusting any check), and the tenant app's **service
worker** cached an old POS bundle, which masked the B-07 fix entirely until it was unregistered.

## What works

The load-bearing flows are sound. Verified end-to-end, not merely rendered:

- **Bank-transfer subscription lifecycle, full round trip.** Tenant opened an overdue invoice →
  bank details with the IBAN correctly masked to last 4 → uploaded a receipt → proof stored on
  local disk → appeared in the admin verification queue → receipt rendered from the signed URL →
  Approve → invoice `paid` → **tenant restored `cancelled` → `active`**. The restore is correctly
  gated on `unpaidLeft === 0`: verifying the first of two outstanding invoices deliberately left
  the tenant locked, and only the second one reactivated it. That is the differentiator and it
  holds up.
- **POS cash sale.** Opened a shift with an EGP 500 float, rang Espresso ×2 + Affogato, took cash
  with change due, completed. Sale persisted at 16000 cents `paid`; `stock_movements` recorded
  `sale −2 ESP-001` and `sale −1 COL-004`. Inventory committed on completion, ledger-first, as
  specified. Receipt page renders correctly and — notably — formats money correctly (`EGP 160.00`).
- **Auth, both realms.** Tenant login; admin login with mandatory TOTP MFA.
- **Impersonation gating.** Modal requires a typed, audited reason and states the constraints.
  The handoff is a single-use 60-second code — never a JWT in the URL — behind a "Support sign-in"
  confirmation interstitial. `impersonation_started` was double-logged to `platform_audit_log`
  **and** the tenant `audit_log` at the same instant, per CLAUDE.md. (The exit is a different
  story — B-04.)
- **Arabic / RTL.** `dir="rtl"`, IBM Plex Sans Arabic loading on demand, full layout mirror,
  Arabic-Indic numerals on the dashboard, correct `ج.م` currency, translated navigation and
  content. Genuinely good.
- **Dark mode (tenant).** Resolves from `prefers-color-scheme` with no light flash.
- **Route boundaries.** `/en/does-not-exist` returns a real HTTP **404** with the branded page;
  route skeletons render with reserved heights during navigation.
- **Single-language name entry itself.** An Arabic-only name posted as
  `name_i18n: {en: "قهوة تجريبية", ar: "قهوة تجريبية"}` — the mirror-at-write invariant works.

## Findings

### B-01 — Inventory table: every column reads one header to the left · **HIGH**

> **Fixed** in `9817e7b`.

On `/[locale]/inventory` the table body is offset one column from its header. Confirmed three
independent ways: visually (zoom), by per-cell geometry, and by the page's own hit-testing —
`document.elementFromPoint` at the centre of each header, on the first data row:

| Header | Value actually under it | What it really is |
|---|---|---|
| Product | `COL-004` | the SKU |
| Price | `Affogato / Cold drinks` | the product name |
| Cost | `£90` | **the price** |
| Margin | `£28` | **the cost** |
| Stock | `69%` | **the margin** |
| Vel/wk | `42` | **the stock** |
| *(blank actions col)* | `0` | the velocity |

The Price column header has nothing beneath it. A shop owner reading this screen gets the price
labelled "Cost" and the cost labelled "Margin".

Not a shared-component bug: `/customers` (6 headers, 6 cells) aligns perfectly. Scoped to
`ProductsTable.tsx`. Present identically in Arabic.

**Root cause (found after the report was written).** `.inv-row::before` — the hover / low-stock
accent stripe — is a generated box on a `<tr>`. A table row may only contain cells, so the browser
wraps that generated content in an **anonymous table cell**, which claims column 1 and pushes all
nine real `<td>`s into columns 2–10. That is why the markup looked symmetric (9 `<th>`, 9 `<td>`,
no stray nodes) while the table resolved to ten column positions. Proven by toggling
`.inv-row::before { content: none }` at runtime: every column snapped into place, and restoring it
broke them again. `.inv-row` was the only row-level pseudo-element in either app, which is why no
other table was affected. The fix re-anchors the stripe to `.inv-td:first-child`.

Files: `apps/web/src/app/[locale]/(shell)/inventory/_components/ProductsTable.tsx:66-205`,
`inventory.css:134-217`. Screenshots: `inventory-column-shift-en-dark.jpg`,
`inventory-column-shift-ar-rtl-dark.jpg`.

### B-02 — A product cannot be saved unless the *optional* description is filled · **HIGH**

> **Fixed** in `6287c4c`.

Regression from `3811809`. `ProductForm` sends `description_i18n: null` when Description is left
empty. The API schema accepts `undefined` but not `null`:

```
POST /v1/products → 400
{"code":"validation_failed","fields":{"description_i18n":"Expected object, received null"}}
```

Proven by differential: the identical payload with `description_i18n` as an object returns **201**.
The UI labels the field "optional".

`create-product.dto.ts:6-11` declares `I18N_TEXT_OPTIONAL` as `.optional()` without `.nullable()`,
while every neighbouring optional field on the same schema uses `.nullable().optional()`
(`category_id`, `tax_class_id`, lines 31-32). Same omission in `update-product.dto.ts:6-11`, so
clearing a description on edit will fail too.

**Scoped precisely: products only.** The equivalent `I18N_ADDRESS_OPTIONAL` in
`create-branch.dto.ts` and `create-supplier.dto.ts` both correctly carry `.nullable()`.
Fix is one word in two files.

### B-03 — Every full-width shell banner renders at the bottom of the page · **HIGH**

> **Fixed** in `28e11ec`.

`SubscriptionBannerShell` and `ImpersonationBanner` both use `gridColumn: "1 / -1"` with
`position: sticky; inset-block-start: 0`, inside a parent that is
`display: grid; grid-template-columns: 240px 1fr`. With no explicit `grid-row`, auto-placement
puts them in a **new row after sidebar + main** — the page footer. Sticky cannot save them: they
are stuck to the wrong row.

Measured:

- Cancelled-tenant banner: `y = 1051` in a 688px viewport.
- Impersonation banner: `y = 1580` of a 1630px document.

Consequences:

- A suspended or cancelled tenant is redirected to `/billing` from every page with **no visible
  explanation** — the "Account cancelled" banner is real, correct, and off-screen.
- **An admin impersonating a tenant sees an ordinary-looking tenant app.** CLAUDE.md requires a
  danger-coloured banner naming the tenant and the admin; the markup is right, the placement makes
  it invisible without scrolling to the footer. This is the security-relevant one.
- Also affects the trial-ending and grace-period nudges.

Files: `_components/SubscriptionBanner.tsx:134-148`, `_components/ImpersonationBanner.tsx:53-59`.
Screenshots: `billing-banner-at-page-bottom-en-dark.jpg`, `impersonating-no-visible-banner.jpg`.

### B-04 — Exiting impersonation writes no audit entry · **HIGH**

> **Fixed** in `3a58a9c`.

After clicking "Exit impersonation" (which correctly returned to the admin app), neither log
contains an end record:

```
platform_audit_log:  impersonation_started × 2      audit_log:  impersonation_started × 2
```

No `impersonation_ended` in either. The backend does write one
(`admin/impersonation/impersonation.service.ts:192,203`), and `admin/audit/audit.service.ts:124-180`
pairs started/ended rows to materialise sessions — so these sessions will render as permanently
open in the Login-as audit.

`ImpersonationBanner.tsx:39-51` calls `POST /v1/impersonation/exit` but **swallows `ApiError`
silently** and redirects in `finally` regardless, so a failed exit is invisible to the operator.

**The underlying cause is worse than a missing audit row.** The handoff ends with
`window.location.replace()` — a full page load — and the auth store has no persistence, so the
impersonation access token was discarded immediately. `AuthBootstrap` then fell back to
`/v1/auth/refresh`, which mints an **ordinary** tenant token: `mintPair` carries no
`impersonator_id`, and `mintImpersonationAccess` mints no refresh half, so the claim was
unrecoverable. The banner survived only because it read `sessionStorage`.

So a moment after "Continue as support", the admin was browsing on the **target user's own
session** with a cosmetic banner over it: actions were attributed to the tenant user rather than
double-logged to the impersonator, and `exit()` failed with `not_impersonating` — which is why the
audit had starts that never ended.

The token is now persisted with the session in `sessionStorage`, `AuthBootstrap` prefers it over
the refresh cookie, and exit only tears down on success. Verified live: after the handoff,
`/v1/impersonation/me` reports `active: true` with the impersonator's email, and exiting writes
`impersonation_ended` to **both** logs.

### B-05 — The seed auto-cancels its own demo tenant · **HIGH** (DX/demo)

> **Fixed** in `7a9bb64`.

`seed.ts` sets the tenant `active` but hardcodes invoice due dates of 2026-05-31 and 2026-06-30.
On any date past roughly 2026-08-06 the billing lifecycle marches it forward on API boot —
overdue → grace (+7d) → suspended (+30d) → **cancelled** — so a freshly seeded demo tenant is
locked out of the entire app on first login (combined with B-03, with no on-screen explanation).
Make the seed dates relative to `now`.

### B-06 — English UI renders EGP money as `£` and `$` · **HIGH**

> **Fixed** in `4482c62`.

The tenant is EGP. In English:

- Dashboard KPIs and branch cards: `£810`, `£740`, `£270`, `£160` (`£` looks like a truncated `E£`)
- Inventory: `£26,056` on-hand, `£90`, `£28` per row
- POS: tiles `£35`, `£90`; cart total `£160` — directly beside its own label reading `TOTAL · EGP`
- Billing: `$149/month`, plan comparison `$10 / $49 / $149 / $399 / $999`, pay wizard
  "Send $149.00 by bank transfer" — while the bank-details block on the same screen says
  `Currency EGP`
- Admin verification queue and proof detail: `$149.00`, `$10.00`; tenant-detail invoices `$149`

Correct in: the receipt (`EGP 160.00`), POS cart line items (`35 EGP each`), the pricing form
(`Price (EGP)`), and **all of Arabic** (`ج.م`).

**Correction — this was two unrelated defects, and one of the "correct" screens was not.**

- The **`$`** sites were passing the right currency code all along. The seed priced all plans and
  both subscription invoices in **USD** while the tenant and the platform receiving bank account
  were **EGP** — correct rendering of incoherent data, telling an Egyptian shop to wire USD into
  an EGP account. `docs/billing-flow.md:179` says the invoice total is in the *tenant's* currency.
  Demo plans are now EGP and the invoice/proof currencies derive from the plan so they cannot drift
  again; signup's default moved from USD to EGP.
- The **`£`** was a literal `if (currency === "EGP") return … "£"` inside a `symbolFor()` helper
  copy-pasted into four dashboard components, plus five more literals in POS and inventory. The
  fallback branch beside it was already correct. Replaced by a shared `currencySymbol()`.
- **`admin dashboard/tenants (EGP 149)` was not correct** — see B-19.

### B-09 — `pnpm db:seed` fails out of the box · **MEDIUM** (DX)

> **Fixed** in `7a9bb64`.

### B-19 — Admin MRR is labelled with the wrong currency · **HIGH** *(found while fixing B-06)*

> **Fixed** in `4482c62`.

Not caught by the walkthrough — the card *looked* right, which is why B-06 above originally listed
it as correct. `admin/dashboard/dashboard.service.ts` sums `plan.monthly_price_cents` but takes the
label from `tenant.default_currency_code`. With the seed's USD plans on an EGP tenant it reported
USD subscription revenue as EGP, and with plans in more than one currency it would silently add
amounts that cannot be added. The 90-day trend SQL had the same defect.

Now grouped by the plan's own currency: the figure and its label always describe the same set of
plans, and the trend query is constrained to the reported currency. A regression test creates
tenants trading in EGP on a USD plan and asserts the MRR is labelled USD.
