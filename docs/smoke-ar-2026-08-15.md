# Arabic UI smoke test — tenant app (`apps/web`), 15 Aug 2026

Browser walkthrough of the tenant app in **Arabic / RTL**, dark mode, against the demo
tenant (`owner@acme.test`, Bayt Coffee Co., EGP, 5 branches) with the API, web and admin
servers running locally.

**Pages exercised:** login · dashboard · inventory (list, category filter, product create
form) · POS (grid, cart, payment sheet, cash + bank-transfer tabs, shift bar) · sales
records · customers · billing (plan & usage) · reports (P&L, tax) · settings (security,
appearance, business) · suppliers · 404.

**Method:** visual inspection plus scripted DOM probes on every page for untranslated
Latin text, raw i18n keys, mixed numeral systems, physical CSS utilities, forced-LTR
subtrees, and horizontal overflow. Where a defect could plausibly be locale-independent
it was re-checked in English before being classified.

## Findings

### AR-01 · Bank transfer is unreachable at the POS — **blocking, not Arabic-specific**

Selecting **تحويل** (bank transfer) in the payment sheet renders an empty panel, and the
only action — "متابعة إلى الإيصال" — is permanently `disabled`. The payment method can be
chosen but never used, in either locale.

Circular dependency in `apps/web/src/app/[locale]/pos/_components/PaymentSheet.tsx`:

```ts
// :100
const transferOk =
  method !== "tx" || (receiptRef.length > 0 && receiptFile !== null && payerName.trim().length > 0);
// :104
const canConfirm = useBottomRow && cashOk && transferOk && !submitting;
// :410
<button disabled={!canConfirm} onClick={() => { if (method === "tx") setStage("receipt"); … }}>
```

The button that navigates to the `receipt` stage is gated on `transferOk`, but the receipt
reference, receipt file and payer name are inputs that **only exist on that stage**. The
gate can never open.

The tenant does have an active default EGP receiving account
(`GET /v1/tenant-bank-accounts` returns Banque Misr ••8821), so this is pure control-flow,
not missing data. `docs/billing-flow.md` makes the POS bank-transfer flow a headline
feature; today it is dead.

**Fix:** gate the compose-stage button on method selection only; keep `transferOk` for the
receipt-stage submit at `:591`, where it already belongs.

### AR-02 · Switching language silently flips the app to light mode — **high**

Reproduced deterministically. On `/ar/customers`, `data-theme="dark"`, body
`rgb(22,19,16)`. Click the globe → `/en/customers`, `data-theme` is **`null`** and the body
is `rgb(250,247,242)`. Loading `/en/customers` directly is dark. The system preference is
dark throughout.

Root cause — `apps/web/src/app/[locale]/layout.tsx:34-43`:

```tsx
const THEME_INIT = `…document.documentElement.setAttribute("data-theme",t);…`;   // :14
…
<html lang={locale} dir={dir} data-accent="terracotta" className={fontVariables} suppressHydrationWarning>
  <body>
    <script dangerouslySetInnerHTML={{ __html: THEME_INIT }} />                  // :43
```

`<html>` is rendered by the **locale layout**, and `lang`/`dir` are props of it. A locale
switch is a route change within that segment, so React re-renders `<html>` — and because
`data-theme` was set imperatively by the inline script rather than declared as a prop, the
re-render **drops the attribute**. The `<script>` in `<body>` does not re-execute on a
client transition, and `ThemeWatcher` (`:49`) does not re-apply it.

For a bilingual product this is the single most-used control in the app, so the regression
is very visible.

Secondary: `THEME_INIT` is duplicated between `layout.tsx:14` and `lib/theme/theme.ts`
behind a "keep in sync" comment, and its `catch` branch defaults to `light` — the wrong
fallback for a system-dark user.

### AR-03 · P&L and Tax reports render in USD for an EGP tenant, and return nothing — **high**

`/ar/reports/pnl` shows a `USD` currency field and every figure as `‏٠٫٠٠ US$`. The tax
report likewise sits on `USD`. Both then report **zero** for a period that contains a real
EGP sale — the currency filter excludes it — so the P&L reads as "no revenue".

```ts
// apps/web/src/app/[locale]/(shell)/reports/pnl/pnl-client.tsx:68
const tenantCurrency = tenant?.default_currency_code ?? "USD";
// :72
const [currency, setCurrency] = useState<string>(tenantCurrency);
```

`useState` reads its argument **only on first render**. On a hard load the auth store is
still empty, so `"USD"` is frozen into state and nothing re-syncs it when the tenant
arrives. `/v1/auth/me` does return `default_currency_code: "EGP"`.

Same pattern at `reports/tax/tax-client.tsx:41-43`. `movers-client.tsx:47` and
`trends-client.tsx:52` read the value on every render, so they self-correct — but all four
carry a `?? "USD"` fallback that no longer matches the product's EGP defaults.

### AR-04 · POS cart and payment sheet ignore Arabic number and currency formatting — **high**

The same price renders two different ways on one screen: `ج.م.٢٤٠` in the product grid,
`240` and `EGP 240 للوحدة` in the cart line directly beside it.

Measured DOM:

| Element | Renders |
|---|---|
| Product tile | `ج.م.٢٤٠` |
| Cart line unit price | `240 EGP للوحدة` |
| Subtotal | `330` |
| Grand total | `ج.م.330` ← Arabic symbol, Western digits, **one value** |
| Total kicker | `الإجمالي · EGP` |
| Pay button | `ادفع330` |
| Payment sheet | `فاتورة #2848`, `330 EGP`, `↑50 350 EGP`, `الباقي 70 EGP` |

The grand total mixing `ج.م.` with `330` is the clearest single symptom — one value, two
locales.

### AR-05 · Phone numbers display backwards — **high**

The customers table shows `201009998877+`. The DOM holds the correct `+201009998877`; the
cell computes `direction: rtl` with no `dir` attribute, so the bidi-neutral `+` is
reordered to the visual right of the digit run.

```
cls "cu-muted" · dir null · direction rtl · unicode-bidi isolate
```

`unicode-bidi: isolate` isolates the run but does not give it an LTR base direction. Needs
`dir="ltr"` (or `unicode-bidi: plaintext`) on any cell holding a phone number, IBAN,
account number or other LTR-structured identifier. Renders correctly in English.

### AR-06 · Numeral systems are mixed throughout — **medium, systemic**

Anything formatted through `Intl` becomes Arabic-Indic (`ar` defaults to the `arab`
numbering system); anything interpolated into a message template stays Western. Both appear
side by side on nearly every screen.

| Page | Arabic-Indic | Western, same screen |
|---|---|---|
| Dashboard | `٨١٠ ج.م.`, `٧٤٠`, `١` | `21 منتجات بدون مخزون`, `ثقة 100٪`, chart axis `30d 23d 16d 9d 1d` |
| Inventory | `٢٢ منتج`, `٢٦٬٠٥٦ ج.م.`, `٥ منخفض` | category chips `إسبريسو6` … `منتجات0`, `عرض 22 من 22` |
| Sales | `‏٢٧٠٫٠٠ ج.م.‏`, `١٥‏/٠٨‏/٢٠٢٦` | items `3`, `صفحة 1 من 1`, `1 من 1` |
| Customers | `قبل ١٣ ساعة` | sales `0` / `1`, `3 من 3` |
| POS | tile prices, chip counts | entire cart, clock `21:55` |
| Everywhere | — | branch picker `5 فروع` |

Root cause for the API-generated strings —
`apps/api/src/tenant/dashboard/dashboard.insights.i18n.ts:90-95`:

```ts
return template.replace(/\{(\w+)\}/g, (match, key) => {
  const value = vars[key];
  return value === undefined ? match : String(value);   // no locale formatting
});
```

Related, same file:

- `:49` the Arabic string hardcodes `48` in Western digits — `"…منذ أكثر من 48 ساعة"`.
- `:59` `"{count} {noun} بدون مخزون"` builds Arabic grammar by swapping a noun. Arabic has
  six plural categories; 11–99 takes the **singular accusative**, so the rendered
  `21 منتجات` should be `٢١ منتجًا`. Only an ICU `{n, plural, …}` form can express this,
  and these templates are hand-rolled.
- `:79` `"أسبوع ثابت — {revenue} عبر {transactions} عملية بيع"` renders as
  **`أسبوع ثابت — 810.00 EGP عبر 1 عملية بيع`** — unformatted money with a raw ISO code
  inside an Arabic sentence.

Note `:69` correctly uses the Arabic percent sign `٪`, while the inventory margin column
does not (see AR-11) — the inconsistency is internal, not just English-vs-Arabic.

### AR-07 · Billing statuses and dates are hardcoded English — **medium**

`/ar/billing` shows the badge **`In review`** and the due date **`Aug 18, 2026`**.

```ts
// apps/web/src/app/[locale]/(shell)/billing/billing-client.tsx:21-28
const INVOICE_TONE = {
  paid:             { …, label: "Paid" },
  awaiting_payment: { …, label: "Awaiting transfer" },
  in_review:        { …, label: "In review" },
  overdue:          { …, label: "Overdue" },
  draft:            { …, label: "Draft" },
  cancelled:        { …, label: "Cancelled" },
};
// :59
function shortDate(iso) {
  return new Date(iso).toLocaleDateString("en-US", { … });   // ignores `locale`
}
```

Six user-facing strings bypass `next-intl` entirely — the lint rule that is supposed to
forbid this did not catch them. `shortDate` sits directly below `formatCents`, which
*does* switch on `locale` to `ar-EG`, so the file is internally inconsistent.

### AR-08 · The API ships English display strings to the client — **medium**

`/ar/reports/pnl` prints **`Custom range`** as its period heading.

```ts
// apps/api/src/tenant/reports/pnl/pnl.service.ts:370-374
const m = f.toLocaleString("en", { month: "long", timeZone: "UTC" });
return `${m} ${f.getUTCFullYear()}`;
…
return "Custom range";
```

The API formats period labels in English and the tenant app renders them verbatim, so
Arabic users also get "August 2026". Per `CLAUDE.md` the API localizes through
`nestjs-i18n`; better still, return a machine-readable period descriptor and let the client
format it.

### AR-09 · Sales list shows the branch **code**, not the localized name — **medium**

The sales table and the dashboard's recent-transactions card both render `zamalek`. Every
branch has a proper pair — `{"en":"Zamalek","ar":"الزمالك"}` — and the branch **dropdowns**
render it correctly, so the data is there.

The API never sends it:

```ts
// apps/api/src/tenant/sales/sales.service.ts:854
branch_code: branchById.get(r.branch_id) ?? "",
```

`GET /v1/sales` returns `branch_code` and no `branch_name_i18n`. Wrong in English too
(lowercase slug), but in Arabic it is a Latin slug in an otherwise fully Arabic table.

Same shape at `TenantBankAccount`: the schema has `name_i18n Json`
(`packages/db/prisma/schema.prisma:481`) but `GET /v1/tenant-bank-accounts` omits it and
returns only the Latin `bank_name`, so a receiving account can never be shown in Arabic.

### AR-10 · Raw enum values and identifiers in Arabic settings — **medium**

`/ar/settings/business`:

- Subscription block shows **`growth`** and **`active`** — raw enum values where "النمو"
  and "نشط" belong. The billing page translates the same plan correctly, so the strings exist.
- **Currency** picker lists bare ISO codes (`USD EUR GBP EGP SDG SAR AED KWD …`),
  **Country** shows `EG`, **Timezone** shows `Africa/Cairo`. The month picker right beside
  them *is* translated (`يناير`…), so the pattern is established and these were skipped.
- The "go to" affordances use a literal **`→`** ("إدارة فئات الضريبة →", "إدارة الاشتراك →")
  pointing right in an RTL page. As text, `rtl:rotate-180` cannot help — they need mirrored
  glyphs or Lucide icons.

### AR-11 · Margin column renders the percent sign on the wrong side — **medium**

The inventory margin cell holds `"٧٨%"` and displays as **`%٧٨`** — a trailing Western `%`
after Arabic-Indic digits is bidi-reordered to the left. Use the Arabic percent sign
`٪` (U+066A) or `Intl.NumberFormat("ar-EG", { style: "percent" })`, both of which yield
`٧٨٪`. The dashboard already does this correctly in one place (`{pct}٪`).

### AR-12 · Shift bar uses English duration units — **medium**

The POS shift chip reads `مفتوحة · 12h 47m · رصيد ٥٠٠٫٠٠ ج.م.` — English abbreviations and
Western digits between two correctly-formatted Arabic fragments. The clock reads `21:55`.

### AR-13 · Native date inputs are US-formatted and LTR — **medium**

Sales and both report pages use bare `<input type="date">`, which renders in the **browser's**
locale, not the page's: `08/15/2026`, left-aligned, in an otherwise RTL form. An Arabic
(ar-EG) user expects `١٥/٨/٢٠٢٦`. Either localize the control or replace it with a
token-driven date picker.

---

### AR-14 · Arabic-Indic numerals and the Hijri toggle do not exist — **medium, spec gap**

`CLAUDE.md` requires both ("Arabic-Indic numerals option, Hijri toggle"; i18n rules 8–9:
"Western digits default; Arabic-Indic optional in tenant settings" and "Gregorian default;
Hijri toggle in tenant settings"). Neither control exists in any settings page, and a
repo-wide grep for `numeral|hijri|arabic_indic|nu-arab|calendar_system` returns **nothing**
in `apps/web/src` and **nothing** in the Prisma schema.

The current behaviour also contradicts the stated default: `ar` renders Arabic-Indic
unconditionally wherever `Intl` is used, because that is `Intl`'s default numbering system
for Arabic — nobody chose it. Resolving AR-06 means deciding this first: pick the default,
add the setting, and thread a resolved locale (e.g. `ar-EG-u-nu-latn`) through every
formatter.

### AR-15 · Lower-severity / not Arabic-specific

- **404 renders in light mode** while the app is dark (`/ar/inventory/new`). Same class as
  AR-02 — a route that misses the theme attribute.
- **Form errors are not announced.** Validation text ("مطلوب") is plain text inside the
  `<label>`, with no `role="alert"` and no `aria-invalid`/`aria-describedby`. Screen-reader
  users get nothing. Affects both locales.
- **Sales pagination bar wraps** — "صفحة 1 من 1" breaks onto two lines and stretches the
  Previous/Next buttons to 47px, splitting their chevrons onto a second line. Reproduces in
  English at the same width, so it is a layout bug, not an RTL one.
- **POS bank-transfer panel has no empty state.** Beyond AR-01, the selected-method panel
  renders nothing at all — no bank details, no QR, no explanation for the disabled button.
  `CLAUDE.md` forbids shipping UI without empty/loading/error states.

## Cleared — checked and not defects

- **Login layout mirroring** — the split panel flips correctly; my first read of the
  screenshot was wrong, the grid maths confirm it.
- **Sales date/time formatting** — `١٥‏/٠٨‏/٢٠٢٦، ٨:٢١ ص` is correct ar-EG output; the
  apparent `YYYY/M/D` ordering in the screenshot is bidi rendering, not the stored string.
- **"الباقي" clipping** in the payment sheet — the glyphs are complete; `scrollWidth ==
  clientWidth`, no overflow. A low-resolution artifact.
- **Plan name mojibake** — `/v1/auth/me` appeared to return `ط§ظ„ظ†ظ…ظˆ`. The database holds
  `النمو` and a byte-accurate re-read of the API response returns `النمو`.
  The corruption was in my shell pipeline's console encoding, not in the app.
- **Customer and cashier names in Latin** (`Aya Mostafa`, `Tamer Khaled`) — seed data, not
  an i18n defect.
- **`Esc` key name and `V60` product name in Latin** — correct as-is.
